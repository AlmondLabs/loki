# pi-durable, pi-ai and chord from 1.1.0 to 1.4.0

## Why

loki pins the three pi libraries at exact versions (the update policy: loki never updates them by itself) and is on
1.1.0, from 7 October. 1.4.0 came out on 21 October. Nothing forces the move, but 1.2–1.4 fix things loki's agents
run into:

1. **OpenAI and Codex**: `gpt-6.1-sol` on Codex gets its 500K context window instead of 272K (pi-ai 1.3). Whitespace-only
   tool output, such as a bare `\r\n` from `bash`, no longer makes OpenAI requests fail with a 400 (pi-ai 1.4). The
   prompt cache survives deferred tool loads (1.4).
2. **After a compaction**, the system baseline leads the context again. In 1.1, Anthropic and Codex requests got it as a
   mid-conversation system message without the initial prompt or tools (pi-durable 1.3).
3. **More transient errors are retried**: gateway upstream failures, "service temporarily unavailable" (which also
   failed compactions), dropped streams (pi-ai 1.2–1.4). And the backoffs now sleep durably, so a restart during one no
   longer starts the wait over (pi-durable 1.4).
4. **A crash loop stops**: a task cut off by a crash five times in a row is parked and reported, not rerun forever
   (pi-durable 1.4).
5. Malformed tool-call arguments fail validation instead of running with half their fields (pi-ai 1.3).
6. The model catalog: models providers retired are gone, and new ones are listed.

## What changes in loki

Installing 1.4.0 and type-checking finds 44 errors in 17 files, all from two changes:

1. **A tool's result is `output`, not `content`** (pi-durable 1.2): every `execute` loki writes returns
   `{ output: [...] }`. That covers `daemon/background.ts`, `memory.ts`, `tools.ts`, `schedule.ts`, `subagents.ts`,
   `ask.ts`, `skills.ts`, `web-search.ts` and `mods/registry.ts`, plus the fakes in three tests and
   `test-node/trial-registry.ts`.
2. **Every `defineDoc` names its `checkpointWhen`** (pi-durable 1.4): `ChatIndex`, `ChatDoc` and `AgentInfoDoc` in
   `daemon/kernel/index.ts`. They are small and change whole, so `() => false` keeps them as they are. Without it,
   `ChatDoc` loses its type, and every place that reads it fails (the other 30 errors).

Changes the compiler cannot see, each checked by hand or by a test:

1. **A failed command reads the same.** `bash` still ends a nonzero exit with `<harness>[error] Command exited with code N</harness>`,
   so plan 036's `errorOf` keeps working; a test pins the wording.
2. **A storage error now closes the Session** (pi-durable 1.2). loki already reopens a store whose Harness closes
   (`StoreManager`, `subscribeClose`), so this needs no new code, only a test that a closed store reopens.
3. **Retry backoffs sleep** (pi-durable 1.4): while a run waits to try a model again, its task is `sleeping`. A chat
   must still show as working (`busy` reads `LiveDoc.run`), and Stop must still stop it. Check both.
4. **After a failed run, queued inputs stay queued** (`settings.afterFailedRun`, default `keep`). A message sent while
   a run fails would then wait. Check whether it waits for the next message; if it does, set `continue`, so the next
   run starts with it. It did (and did on 1.1 too), so `AgentStore.open` sets `continue` for every store.
5. **`TaskRuntime` and `ToolExecutionApi` gained members** (`sleepUntil`, `setTimer`, `now`). Test fakes that build them
   by hand need them, and the type checker finds those.
6. **chord**: loki uses only `Context`, `BACKGROUND_CONTEXT` and `withCancel`, not chord's host runtime that 1.2–1.3
   replaced. 1.4 requires `Context.telemetry` of custom contexts; loki makes none of its own.

## The store migration, and its backup

1. **What happens**: when 1.4 opens a chat store (`~/.loki/stores/<agent>.sqlite`), it migrates the store's schema from
   version 1 to 2 (the `durable_schema` table), rebuilding its `tasks` table. **A migrated store cannot be opened by 1.1
   or 1.3**, so going back means going back to a copy.
2. **The copy**: before `AgentStore.open` opens a file, it reads `durable_schema.version`. When that is below
   pi-durable's `CURRENT_SQLITE_SCHEMA_VERSION`, it first copies the store whole with `VACUUM INTO`, which carries what
   the write-ahead log holds too. The copy goes to `~/.loki/stores/backup-schema-<from>-<date>/<agent>.sqlite`. It is
   the same copy `npm run shrink-images` makes (`daemon/store-images.ts`), moved to a helper both use.
3. **Once per store**: a store already at version 2 is opened as it is. A copy that fails stops that store from opening,
   with a report: better a chat that waits than a store that cannot go back.
4. **The copies stay** until the person deletes them. The manual says where they are, and that they are the way back
   to an older loki.
5. **Other Macs**: each Mac's stores are its own, so each Mac migrates and copies its own on its first start. A paired
   Mac on the old loki keeps working with its own stores. Chats moving between the two are checked below.

## Tests

1. The type checker, the whole test suite and the node tests on 1.4.0, with the fakes updated.
2. **The backup**: a store file whose `durable_schema` says 1 is copied before it opens, and the copy still says 1;
   one at 2 is not copied; a copy that fails keeps the store closed and reports it.
3. **The wording of a failed command**: a `bash` call with a nonzero exit through the 1.4 harness ends with the
   `<harness>` note `errorOf` reads.
4. **A closed store reopens**: a store whose storage throws closes its Session, and the next `get` opens it again.
5. **A message queued behind a failed run** is answered next, without another message.

## Checked by hand

1. **A copy of a real store**: copy the stores (read-only) into a scratch loki folder and start a daemon on it. Every
   chat opens, its history reads the same as on 1.1, a turn runs, and the backup folder holds the version-1 copies.
2. **Demo Macs**: the two paired demo daemons on 1.4: a chat moves between them, the phone pairs and reads, and a
   scheduled task fires.
3. **A retry**: with the network off for a moment, a turn retries (the chat shows working, Stop works) and then
   answers, or ends as plan 037's row.
4. **A queued message after a failed run** (item 4 above).

## Checked so far (2026-10-26)

1. All checks pass on 1.4.0: format, lint, types, the test suite, the node tests, both builds and smoke.
2. **A copy of the real stores**: three stores (191 chats, 39,299 entries) were copied with `VACUUM INTO`, read
   with 1.1 from the main checkout and with 1.4 from this branch. 1.4 copied each store to
   `backup-schema-1-<date>/` (still version 1), migrated it to version 2, and every chat's title, entry count and
   folded history read the same as on 1.1. The live stores stayed at version 1.
3. **Demo Macs** (two throwaway paired daemons on the 1.4 bundles, a fake model, made-up data): a chat made on one
   moved to the other with its history, took a turn there, and moved back; a message sent to the Mac it left went on
   to the Mac it lives on. Both stores were made at version 2. A phone paired with a code and read the chat. A
   scheduled task the agent set fired in the next minute and was answered.
4. **A retry**, with the network off: the turn tried four times (2, 4 and 8 seconds apart) and showed as working all
   along. With the network back mid-wait it answered; left off, it ended as plan 037's row ("4 tries"). Stop during a
   wait ended the turn at once, with no more tries.
5. **A message queued behind a failed run** waits, as item 4 above feared: it is not shown, and runs only when the next
   message is sent. 1.1 does the same. loki now sets `afterFailedRun: "continue"`, so the waiting message starts the
   next run on its own; a test in `test/kernel.test.ts` holds it (it times out under `keep`). Seen on the way, the same
   on 1.1 and left for later: Stop during a retry leaves "the model could not be reached" rather than a stopped turn.

## Not in this plan

1. pi's new features (durable sleeps for loki's own tasks, `onWake`, compaction per model, telemetry) beyond what the
   upgrade needs.
2. Moving to 1.4.x patch releases later: the same steps, without the migration.
